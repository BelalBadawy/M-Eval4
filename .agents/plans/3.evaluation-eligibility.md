# Plan 3: Evaluation Eligibility (Module 3 — `ELIG`)

✅ **Simple** — The eligibility predicate is exactly one condition: `IsEvaluationEligible == true`. Incorporates the accepted full-sync "Reset-Then-Import" transactional reset, blast radius reporting (`absentResetToIneligible`, `flagSetEligible`, `flagSetIneligible`), strictly required `1`/`0` flag parsing in HR import, flip of existing Module 2 local-column-preservation tests, an ultra-lean `EligibilityService`, three read endpoints (`summary` with per-company breakdown, `employees` defaulting to eligible, `excluded` with single reason `hr-flag-false`), bulk flag update (`bulk-flag-update` with AllOrNothing validation and symmetric IP audit), and the complete test suite including test cases `ELIG-9` through `ELIG-14`.

## 2. Architecture & Design Decisions

### A. The Predicate Is One Condition
$$\text{Eligible} \iff \text{IsEvaluationEligible} == \text{true}$$

- **EmploymentStatus & IsActive are informational for eligibility**:
  - Resigned or terminated employees can participate in evaluations if HR included them in the file with flag 1 (e.g., year-end evaluation for employees who resigned during the cycle).
  - Per `ORG-026`, their linked `User` account is deactivated (cannot log in to the portal), but their `Employee` record remains eligible for evaluation by their manager.
  - `IsActive = false` (a theoretical data-correction flag) does not second-guess the file flag.
- **Single Exclusion Reason**:
  - `GET /api/v1/eligibility/excluded` returns a single, unambiguous reason code: `hr-flag-false`. No complex precedence or multi-factor taxonomy.
- **Review-Stage Corrections**:
  - Manual admin adjustments via `PUT /api/v1/employees/{id}/eligibility` or `POST /api/v1/eligibility/bulk-flag-update` survive until the next full-sync import, at which point the file re-establishes authority.

### B. Full-Sync "Reset-Then-Import" in Locked Transaction & P1 Test Flip
- **Local Column Preservation Set Adjusted**:
  - Previously, `IsEvaluationEligible`, `UserId`, and `IsActive` were preserved on update.
  - Now, `IsEvaluationEligible` is **owned by the import**: on upsert, `existing.IsEvaluationEligible = empRow.IsEvaluationEligible;`.
  - Only `UserId` and `IsActive` remain preserved.
- Inside the atomic `AllOrNothing` transaction:
  1. Targeted absent reset:
     ```csharp
     var fileEmployeeIds = parsedData.Employees.Select(e => e.EmployeeId).ToList();
     await _context.Employees
         .Where(e => !fileEmployeeIds.Contains(e.EmployeeId) && e.IsEvaluationEligible)
         .ExecuteUpdateAsync(s => s.SetProperty(e => e.IsEvaluationEligible, false)
                                   .SetProperty(e => e.UpdatedAtUtc, DateTime.UtcNow));
     ```
  2. Upsert lookups in FK order.
  3. Upsert employees: file-present employees receive their explicit file flag.
  4. Offboarding cascade for resigned/terminated employees (deactivates linked user session without touching employee eligibility).
- Rollback on failure: If any validation error or exception occurs, the entire transaction is rolled back.

### C. Import File Strict Flag Validation & Blast Radius Reporting
- **Strict 1/0 Requirement**: In the HR import template, `IsEvaluationEligible` is column 18 and strictly required. Values must be `1` or `0` (or `true`/`false`). Empty or unrecognized strings generate row errors (`IsEvaluationEligible`, "Value must be 1 (Eligible) or 0 (Ineligible)."). Never defaults to true.
- **Blast Radius Metrics**: Both dry-run and execute report:
  - `flagSetEligible`: count of file rows with flag = 1
  - `flagSetIneligible`: count of file rows with flag = 0
  - `absentResetToIneligible`: count of DB employees currently eligible who are absent from the file and will be zeroed.

### D. Bulk Flag Update (`bulk-flag-update`) Semantics
- Endpoint: `POST /api/v1/eligibility/bulk-flag-update`
- Protected by `employees.manage-eligibility`
- Limits: maximum 500 employee IDs per request.
- **Validation Semantics (AllOrNothing)**: If any requested `EmployeeId` does not exist in the database, the entire request is rejected with `400 Bad Request` containing a list of `missingEmployeeIds`.
- **Audit Symmetry**: Extracts `httpContext.Connection.RemoteIpAddress` and writes a single batch summary audit log `EligibilityBulkChanged` with count, target state, reason, and actor IP address (matching `SetEvaluationEligibilityAsync` symmetry).

### E. Query Default Semantics
- `GET /api/v1/eligibility/employees`:
  - When `isEligible` parameter is omitted (`null`), it defaults to `true` (returns the eligible population per `ELIG-004`).
  - When `isEligible = false`, it returns ineligible employees (a secondary filterable view of `/excluded`).
  - When `isEligible = true`, returns eligible employees.
